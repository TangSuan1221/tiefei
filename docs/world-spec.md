## 2. 生成算法（`generator.ts`）

**明确不用 BSP。** BSP 生成的是"矩形房间的密铺"，而潜艇在玩家脑中是**一条脊柱加一堆挂件**。算法是加权图生长，九步：

1. **铺脊柱** — 每层一条主通道，长度 `clamp(round(budget×0.42), 3, 9)`，相邻节点用 `role='critical'` 门连接。脊柱头是该层的 `deckEntry`。
2. **挂锚点** — 每个必需舱段按**脊柱位置亲和度**加权选宿主：
   `w = exp(−(t−affinity)² / 0.09) × (0.55 + fbm2(...)×0.9) × 1/(1+deg×0.25)`
   高斯项让食堂总在前段、压载总在尾段；`fbm2` 扰动让同一原型在不同种子落在不同位置；度数惩罚避免全挂在同一节点上。
3. **长分支** — 按甲板原型权重表生长，宿主选择偏好低度数节点（`1/(1+deg^1.7×0.3)`），脊柱节点 ×2.4 加权。
4. **闭环** — 反复在低度数节点间加横向联络门，直到「入口 → 下行口」的**点不交路径数 ≥ 2**（最大流验证），避免纯树形拓扑。
5. **注入** — 淹水沿门连片扩散（不是逐房间随机）；爬行管道短接拓扑上相距远的两点；秘密舱挂在 `knowledge` 锁后并置 `onBlueprint=false`。
6. **竖向连接** — 每层 2–4 条下行通道。第一条是 `critical` + `unstable=false` + `DESCENT_PLAN` 指定的锁；其余是 `optional`，可以 unstable、可以是爬管、用不同种类的锁。
7. **约束放置钥匙** — 见 §3。
8. **放置 setpiece** — 一律挂在 `optional`/`secret` 门上。
9. **验证 → 重生成 → 兜底修复** — 见 §4。

### 2.1 关键通路提升 `promoteCriticalRoute`

竖井宿主是按"现实里哪种舱段会有竖井"加权挑的，很可能落在一根 `optional` 分支上。于是竖井本身是 `critical`，通往竖井的那段路却不是，悲观求解就够不着。这一步显式地把「层入口 → 主竖井宿主」「起点 → D1 入口」「最深层入口 → 出口」三段路铺成 `critical`，**而不是靠重掷种子碰运气**。

选路只走无锁、非秘密的层内门，且优先避开爬管（关键路径应该是能正常走过去的那条，爬管是玩家主动选的风险捷径）。真找不到无锁通路时直接补一扇关键连络门。

### 2.2 下行锁链 `DESCENT_PLAN`

| 甲板 | 主通道锁 | 备用通道锁 |
|---|---|---|
| D1→D2 | `valve: sys.valve.trunk-a` | `key: item.key.crew-brass` |
| D2→D3 | `power: sys.power.command` | `valve: sys.valve.bilge-c` |
| D3→D4 | `code: know.world.code.sanctum` | `knowledge: know.world.truth.choir` |
| D4→D5 | `ritual: ritual.threshold` | `key: item.key.moonpool-wrench` |
| 月池门 | `valve: sys.valve.moonpool-drain` | — |

五种锁分别对应五种动词（拧、送电、输码、做仪式、找钥匙），保证进度不是重复同一个动作。

## 3. 钥匙放置即约束求解

对每一把关键锁所需的钥匙 `K`：

1. 求 `roomsReachableWithoutKey(graph, K, start)` —— 在**不拥有 K** 的前提下、只走 `critical` 门能到的房间集合 `S`。
2. 判断 `K` 是否**已经在 S 内可得**（`keyObtainableWithin`）。注意判据不是"这把钥匙在图上有没有"，而是"在够得着的地方有没有" —— 随机房间内容本来就可能刷出同一个产出源，但如果它落在需要 K 才能打开的门后面，它等于不存在。
3. 若不可得，从 `unconditionalSourcesOf(K)` 里挑一个 `PropDef`，按 `fits`（原型匹配 ×8，不匹配 ×0.6）、甲板深度、是否锚点加权，塞进 `S` 里的某个房间。

因为放置位置是从"无此钥匙的可达集"里挑的，**钥匙在构造上不可能被锁在它自己开的门后面**。这不是靠重试试出来的。

> 实测：修好第 2 步的可达性判据之后，首次尝试通过率从 **35% 跳到 99.7%**，兜底修复调用次数从 1.33% 降到 **0%**。这一条判据就是整个生成器最重要的一行。

## 4. 求解器与质量闸门（`solver.ts`）

### 4.1 悲观模式

`doorAllowedForSolver(door, pessimistic=true)` 只放行 `role === 'critical' && !unstable && canWalk(state)` 的门；条件门控的交互一律视为不可用；`not` / `vital` / `stigma` 类条件一律判假（它们在前向不动点里不单调）。

含义：**所有可选门锁死、所有不稳定门失效、所有需要前置条件的交互都做不了，游戏仍然必须能通关。**

### 4.2 求解过程

前向不动点迭代，每轮做两件事：

- **采集**：所有已达房间里"能立刻做"的交互，抽出其 `flag/item/knowledge/flag-add` 产出，记入钥匙集并记录获得房间。
- **扩张**：所有已达房间的出边，门允许且锁已持有则并入可达集。

不再变化即收敛（上限 400 轮）。产出 `SolveReport`：可达集、钥匙获得顺序、被挡住的门及原因、关键路径、关节点、每层点不交下行路径数、最深抵达甲板。

关键路径是「起点 → 各必需钥匙房间（按获得顺序）→ 终点」的**行走**而非简单路径，因此允许折返（去拿钥匙再回来）——这正是玩家实际要走的距离，用它衡量关卡长度比简单路径更诚实。

### 4.3 质量闸门 `gradeLevel`

| 条件 | 阈值 |
|---|---|
| 悲观可通关 | 必须为真 |
| 关键路径长度 | ≥ 16 |
| 可选内容占比 | ≥ 0.30 |
| 每层点不交下行路径 | ≥ 2 |
| 最深抵达甲板 | = 甲板总数 |

不合格即重掷（最多 12 次），保留评分最高的一张。

### 4.4 兜底修复 `repairForSolvability`

12 次全不合格时才触发，逐轮做：解开挡在可达边界上的锁 → 解卡死状态 → 把门提升为 `critical/stable` → 仍不行就在可达区最深房间与下一层入口之间架桥 → 最后一道保险是直接连到出口。

它破坏关卡设计（凭空多一条捷径），但"能通关"是不可谈判的，关卡质量是可以谈判的。**它触发一次就说明生成算法有漏洞，统计里看得见。目前 1000 次触发 0 次。**

## 5. 声呐（`sonar.ts`，GDD §4.4）

### 5.1 模式表

| 模式 | 呼吸成本 | 噪音 | 半径 | 保真度 | 分辨力 |
|---|---:|---:|---:|---:|---:|
| Passive 被动聆听 | 2 | 0 | 1 | 0.35 | 0.25 |
| Chirp 短脉冲 | 4 | 9 | 3 | 0.80 | 0.60 |
| Boom 全功率 | 7 | 28 | 7 | 0.98 | 0.92 |

风险—信息三角：Passive 不发声但只看得见隔壁且分不清那是什么；Boom 看得清整层但整条船都知道你在哪。

### 5.2 传播

BFS 能量扩散。门透过率随状态变化：

| open | closed | jammed | sealed | welded | flooded-shut |
|---:|---:|---:|---:|---:|---:|
| 1.00 | 0.72 | 0.66 | 0.34 | 0.18 | 0.56 |

爬管 ×0.52（截面小，高频截断），跨甲板 ×0.62（要穿过一整层甲板钢）。**水封门比焊死门传声更好 —— 水是好导体**，这是可以被玩家利用的物理直觉。

### 5.3 伪影

`pArtifact = (1 − fidelity) × (1 + corruption × 2)`

伪影是**被错误标记为存在的房间**（不是噪点），所以玩家会照着一张多出房间的图去走，然后撞墙。它的可观察破绽是：两次脉冲扫出的回波延迟不一致（`echoFingerprint` 每次抖动）。

### 5.4 异常与签名

每个异常带 `confidence`（随分辨力与距离衰减）与 `signature` —— 一批有质感的短字符串，玩家分不清那是怪、尸体、还是自己的回声。示例：`软组织·移动中`、`金属·规则敲击`、`与你同步的回波`、`密度接近人体·静止`、`空腔·不该在那里`。

### 5.5 多抽头回波

`buildEchoTaps` 按拓扑距离给音频系统输出 `{delay, gain, pan}[]`：`delay` 来自跳数 × 舱段长度 / 声速，`gain` 来自累计透过率，`pan` 来自相对方位角。混响是真实拓扑的函数，所以**关掉画面只听声音也能大致判断船的形状**。

## 6. 非欧重织（`reweave.ts`，GDD §6.3）

关键要求是**可学习，不是随机**。六条规则以文本形式内置，玩家观察到足够次数后由 `insight()` 逐条"解锁"为可读提示：

| 规则 | 内容 | 需观察次数 |
|---|---|---:|
| R1 | 只有某些门会变，门框旁焊着圈里带横线的记号 | 2 |
| R2 | 它从不把你往上送。门后甲板永远同层或更深 | 3 |
| R3 | 它在把你往圣所层推。重连后到 D4 的路总是变短 | 4 |
| R4 | 你脚下这个房间的门不会变，刚走过的那扇也不会 | 2 |
| R5 | 它只重排你已经知道的地方 | 3 |
| R6 | 它从不把路堵死。你总还能走到月池 —— 它要你走完 | 5 |

强度 `intensity = clamp01(pressure×0.7 + min(stigma,12)/24)`，单次最多改 `1 + intensity×4` 扇门。

每次改接都跑 `stillSolvable()` 验证，不通过就**回滚**（`report.reverted` 计数）。R4 和 `applyInstability` 里"关键门永不 unstable"是第一道保险，这个回滚是第二道。玩家不可能被重织困死。

`markDoor(doorId)` / `checkDoorMark(doorId)` 给玩家提供物理标记：在门框上划一道，回来时若标记不在原位，就知道这扇门被重连过。`report.tripped` 列出本次被触发的标记。

## 7. Setpiece（`setpieces.ts`，GDD §6.4）

9 个，全部挂在 `optional`/`secret` 门上 —— **惊喜永远不会变成卡关**。

**GDD 指定的五个（100% 出现）：**

| id | 名称 | 机制 |
|---|---|---|
| `mirror-cell` | 镜像舱 | 与刚走过的房间完全对称，包含你留下的痕迹 —— 但痕迹是左右反的。`mirrorTrace()` 负责镜像化 |
| `mobius-passage` | 莫比乌斯走廊 | 往前走四次回到起点，每次回来房间少一件东西（`removeProps`） |
| `room-zero` | 零号舱 | `onBlueprint=false`，`sonarVisible()` 仅在 SAN<20 时返回真 |
| `drowned-chapel` | 淹没的圣堂 | `flooding=1.0`，全程屏息，`blockSonar=true` |
| `own-quarters` | 你自己的舱室 | 一具穿着你衣服的尸体，日志是你还没写的（`prop.logbook.unwritten-log`） |

**原创四个（各约 75% 出现，预算 2–4 个）：**

| id | 名称 | 机制 |
|---|---|---|
| `pressure-confessional` | 压力告解室 | 密封舱。屏息到某个阈值它才"答话"；答案是真的，代价是一次不可逆的 Stigma |
| `tally-corridor` | 计数走廊 | 墙上凿的正字。数字等于你这一轮死过的次数 —— 它比存档更早知道 |
| `echo-chamber` | 回声室 | 你说一个字，它把整句话还给你。声呐在这里返回的是你**下一次**会扫到的东西 |
| `inverted-ballast` | 倒悬压载舱 | 水从上方来，重力方向与船体相反的一舱。压载阀在"天花板"上 |

每个提供 `build` / `onEnter` / `onExit` / `onPing` / `sonarVisible` 钩子，返回 `SetpieceHookResult`（日志、效果、传送、遮蔽声呐、额外异常、洪水增量、解锁门、移除道具、改名）。

## 8. 内容体量（对照 GDD §9）

| 项 | 门槛 | 目标 | 实际 |
|---|---:|---:|---:|
| 房间原型 | 20 | 20 | **20** |
| 房间变体 | 60 | 100 | **125**（可抽取 116） |
| Prop 定义 | — | 60 | **89** |
| PropKind 覆盖 | 15/15 | | **15/15** |
| 交互定义 | — | | **221**（平均 2.48/Prop，15.4% 带条件门控） |
| Setpiece | 5+3 | | **9** |

每原型变体数最少 4（reactor / bridge / torpedo / airlock），最多 15（corridor）。

`describe(san)` 三档：**清明**（SAN ≥ 60，只陈述可见事实）/ **漂移**（30–60，指出一个说不通的细节）/ **共鸣**（< 30，那个细节的解释成立了）。写法是冷峻、具体、克制的事实陈述，不堆恐怖形容词 —— 恐怖来自"这句话如果是真的意味着什么"，不来自感叹号。

启动时 `assertWorldContent()` 做三项自检：变体 id 不重复、引用的 prop 定义都存在、**每个甲板权重表里的每个原型都至少有一个可用变体**。内容错误宁可启动就崩，也不要在第 700 次生成时变成一个空房间。

## 11. 已知取舍与后续

1. **咽喉比例 58% 偏高。** 关键路径上超过一半的房间是关节点，意味着骨架仍偏线性。根因是悲观模式只认 `critical` 门，而 `critical` 门目前只有脊柱、锚点和被提升的通路 —— 天然是一棵树。下一步应让 `closeLoops` 也产出少量 `critical` 环边，把"两条都保证走得通的路"做进悲观拓扑里，而不只是做进乐观拓扑里。
2. **条件门控交互仅占 15.4%。** 悲观求解会把它们全部作废，所以这个比例低是安全的；但从内容角度，"只有拿到撬棍才出现的选项"应该更多，目前偏少。
3. **`airlock` 在 D2–D4 的权重极低**，导致该原型的变体主要落在 D1/D5。这是甲板权重表的设计选择（中间层本来就不该有很多气闸），不是缺陷，但内容作者需要知道。

## 12. CONTRACT CHANGE REQUEST

`src/core/contract.ts` 未做任何修改。以下是实现过程中发现的缺口，**均已在 world 模块内部自行消化**，列在这里供契约负责人决定是否上收：

### CCR-1 `WorldSystem` 缺少"时间推进"入口（已内部消化）

噪音衰减（−0.8/呼吸）、水位演化、Listener 移动都需要按呼吸推进，但契约里没有对应方法。当前实现为 `World.advance(breaths, rng)`，是**契约之外的扩展方法**。若 sim 层希望通过 `WorldSystem` 接口调用，需要在契约里加：

```ts
advance(breaths: Breaths, rng: Rng): readonly WorldEvent[];
```

### CCR-2 `WorldSystem` 缺少门标记 API（已内部消化）

GDD §6.3 要求"玩家可以在门上做标记来检测重织"。当前实现为 `World.mark(doorId)` / `World.checkMark(doorId)`。若 UI 层需要，契约应加：

```ts
mark(doorId: ID): void;
checkMark(doorId: ID): DoorMarkVerdict;
```

### CCR-3 `SonarResult` 没有承载多抽头回波的字段（已内部消化）

GDD §4.4 要求给音频系统输出 `{delay, gain, pan}[]`。当前实现把它放在 world 内部的 `SonarSweep.taps` 上，通过 `World.sonar()` 返回的扩展结构暴露。若 audio 层要通过契约拿到，`SonarResult` 需要加：

```ts
taps?: readonly { delay: number; gain: number; pan: number }[];
```

### CCR-4 `Prop.describe` 使方法无法序列化（已用 id 编码方案解决，无需改契约）

`Prop` 带方法，`structuredClone` / `JSON` 存档会丢失。解决方式是把定义 id 编码进实例 id（`defId@serial`），读档时用 `rehydrateProp` 从注册表重建方法。副作用是 **Prop 实例 id 不能由外部随意构造**。此约定已在 `props.ts` 顶部注明。

### CCR-5 `RoomArchetype` 没有 `pipe` / `locker` 之类的细粒度原型

内容编写时几次想要"管廊"和"储物间"这两个原型。当前用 `crawlspace` 和 `bulkhead` 代替，读起来略勉强。这是内容侧的愿望，不是阻塞项。
