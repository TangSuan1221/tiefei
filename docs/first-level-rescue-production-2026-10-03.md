# 正式第一关：断桥救援制作与验收

日期：2026-10-03。运行入口为 `/`，不是 `/whitebox.html`。用户已明确本轮同时修改玩法与视觉。

## 实施范围

复用正式首关A检查气闸、C岸电维修湾及A-C弯道/C-B通道。B保留旧压力壳、高位倒悬舱和外围结构，在驾驶高度接入断桥、北侧维修区、隔离货仓和南侧操作位。其余旧房仍保留在几何中但不属于新救援路线，不宣布整个五层战役迁移完成。

新增控制器 `harbor-rescue.ts` 管理故事事实，`harbor-rescue-site.ts` 将其与正式场景/摄影/输入/存档连接；导航通信与场景模型分别独立。新开局在实际A入口驾驶，坐标不传送、不自动推进。

## 摄影与存档

曝光开始只生成待提交快照。连续5秒成功且至少3帧真实传感记录后才提交，取消曝光不能确认怪物入仓。分析使用正式媒体校验和曝光epoch，不读取现时怪物位置伪造旧片。原始照片与分析可重复查阅，重复核验不发奖。

新存档保留救援事实、计时、摄影证据、通信、XYZ航点与声纳记录。旧调查链存档明确不兼容且不删除；用户从标题开始新调查。攻击中不覆盖安全检查点，未完成曝光不保存。

## 用户实玩阻断复核：航点之后不能开门

此前无传送航路测试仍直接调用 `site.move/interact`，没有证明完整玩家输入链可用。用户报告后，独立 Agent 使用鼠标输入XYZ、Space推进、Shift制动，在 `[11,0,18.3385]`、`at=nav`、无驾驶阻断的合法位置按实体F，首门没有打开。原始证据 `qa/harbor/player-playthrough/before-fix.json` 与同名PNG。

根因：点击声纳键盘后上下文为nav，而会话只在camera上下文处理F。已将设施F操作接到统一E操作区的camera/nav/lab三处，保持真实射线与3.4米范围，并兼容物理KeyF。另修入口坐标到位后的过早开门指令：X11/Y0/Z16是接近点，仍需前进到有效距离。仪表显示当前门/面板距离及F条件，失败反馈立即显示，不排在长对白后。

修复后同一真实输入首门已打开且艇体穿过门平面；沿A-C弯道进入维修湾、到第二门按F也已通过。当时仅能确认两道门，之后继续执行完整真实输入救援测试，结果见下。

完整键鼠测试的下一轮实际完成求救通信及第一张底片分析，但在02转向时停滞。面板原宽1.25米、相对艇位(2.2,-2.2)，从0°转到45°的中间姿态撞箱；单独检查最终45°会漏掉。已将三站实体柜体缩窄至0.625米，并移至相对艇位(2.5,-2.43)，碰撞盒与实体同步调整。新检查 `tools/harbor-panel-clearance-check.mjs` 覆盖三站各9个±0.15米停车偏差、0–50°每0.5°连续扫掠以及45°实际可见模型射线，27个位置全部无碰撞且F距离≤3.4米。调整前27点均出现中间角度阻挡。失败实际航行记录见 `panel-turn-block.json`，前后几何报告见 `panel-clearance-before.json` / `panel-clearance.json`（均位于上述player-playthrough目录）。这项几何回归不替代后续完整键鼠通关。
